# Halton-MaskGIT — large 384 / cfg=0.5   LazyMAR 选点复刻 (HALTON_LAZY_VSIM) sweep
#
# Model    : ImageNet_384_large.pth (H-MaskGIT-L, 480M, 24 层 / 1024 dim / 24^2+1=577 token)
# Sampler  : halton, step=32, cfg_w=0.5, fp32, seed=42, global_bsize=32, 50000 imgs
#            —— Halton 顺序 / step gate / 温度 / CFG 与 baseline 完全一致, 未改动。
# Gate     : step 5..30 (与 lazycache sweep 完全相同), REFRESH_N=2
# Layers   : LAZY_START=3 .. LAZY_END=23 (从第 3 层一路用到最后一层)
#
# ============================================================================
# 方案: 只换"选哪些 token 重算", 执行机制与 HALTON_LAZY_CACHE 共用
# ----------------------------------------------------------------------------
# 执行 (不变, 见 results/halton_large384_lazycache_sweep.txt):
#   Q 只算 active token; K/V 走 per-layer 全长缓存 (active 行重算后 scatter 回缓存)
#   —— 双向 self-attention 的上下文保持完整; FFN 只算 active; 区间出口层用缓存回填
#   inactive 行; head 也只算 active 行。
#
# 选点 (本方案的全部改动) —— LazyMAR/models/basic.py 的 _prune_tokens 复刻:
#   score_i = 1 - cos( V_l(t)_i , V_l(t-1)_i )     l = LAZY_START = 3
#             V 取入口层 (layer 3) 的 value, 按 head 求均值后按 token 打分;
#             fp32 计算 (bf16 下近乎相同的 1024 维向量做余弦会丢判别位)。
#   active  = TopK_{k_t}(score),  k_t = ceil(rho_t * N)
#   rho_t   = LazyMAR 的 RETAIN_RATIO_SCHEDULE, 随 step 单调衰减,
#             64 步表按生成进度重采样到 32 步 (idx = floor(2*t)):
#               t = 0..9   -> 1.00      t = 10 -> 0.60     t = 11,12 -> 0.50
#               t = 13,14  -> 0.40      t = 15..17 -> 0.15 t = 18,19 -> 0.12
#               t = 20..31 -> 0.05
#   **没有任何强制 token**: LazyMAR 里 score[mask_to_pred]=0 / +15 名额那一段被
#   整个去掉 —— U_t (本步要 commit 的 token)、U_{t-1}、register 全都只按 V 的变化
#   量竞争名额, 落选就沿用上一步的 logit。这正是本接口要测的东西。
#   CFG 两半 ([cond ; uncond]) 共享同一份分数, 保证选中同一批 token。
#
# 与 lazycache (r=1) 的对照 —— 唯一差别就是上面这一段:
#   lazycache : active = U_t ∪ U_{t-1} ∪ register, 纯调度决定, k/N ≈ 0.0587 恒定
#   lazyvsim  : active = TopK(V 余弦变化量), 内容自适应, k/N = rho_t 随 step 衰减
#               REFRESH_N=2 下 13 个 partial 步的 k/N:
#                 t=6,8 -> 1.00 (退化成全量, 不打分)  t=10 -> 0.60  t=12 -> 0.50
#                 t=14 -> 0.40  t=16 -> 0.15  t=18 -> 0.12  t=20..30(偶) -> 0.05
#               partial 步平均 k/N = 4.07/13 = 0.3131
#
# 起效 step 与 lazy cache 完全一致 (Sampler/halton_sampler.py 的 gate 未改):
#   step 5..30 中, gated_step_counter % REFRESH_N == 0 的步做全量刷新,
#   REFRESH_N=2 -> 刷新落在 step 5,7,...,29 (共 13 步 + gate 外 6 步 = 19 全量步),
#   partial 落在 step 6,8,...,30 (13 步)。
#
# 接口: launch/eval_fid_large384_lazyvsim.sh
#   HALTON_LAZY_CACHE=1 HALTON_LAZY_VSIM=1
#   HALTON_LAZY_VSIM_SCHED=lazymar|<常数>|<逐步逗号表>
#   HALTON_LAZY_START_LAYER=3 HALTON_LAZY_END_LAYER=23 HALTON_CACHE_REFRESH_N=2
#   保护: 未开 HALTON_LAZY_CACHE 或 START_LAYER=0 时直接报错 (layer 0 的输入只在
#   U_{t-1} 处变过, 在那里打分等于退化回调度选点)。
#   测试: python test_lazy_vsim.py (9/9) —— 含"预算 = ceil(rho_t*N)"、"选点确为
#   V 余弦 TopK"、"U_t 确实会落选 (无强制集合)"、"step gate 与 lazycache 逐步一致"。
#   既有方案未受影响: python test_lazy_token_cache.py (16/16),
#                    python test_cache_regression.py (6/6 逐位不变)。
#
# 对照 (同 sampler / 同 seed / 同 gate, 取自 lazycache sweep):
#   baseline (无 cache)              FID 2.5410  IS 256.15
#   lazycache r=1 N=2  (L0-23)       FID 2.6951  IS 252.31   实测 1.552x

#         LAZY_START=0 让 24 层全部进入 lazy 区间。

#

# 【结论】去掉强制集合几乎没有代价 —— 因为它一半是冗余的, 另一半不重要
#
# 实测每个 partial 步 active 集合对强制集合的覆盖率 (真实 checkpoint, batch 4 +
# CFG, 非 randomize, 一次 generation; 探针见下方复现说明):
#
#   step     k     k/N  forced  forced覆盖   U_t  U_t覆盖  U_(t-1)  U_(t-1)覆盖  reg覆盖
#      6   577  1.0000      24     100.0%    11   100.0%       12      100.0%   100.0%
#      8   577  1.0000      25     100.0%    12   100.0%       12      100.0%   100.0%
#     10   347  0.6014      25      76.0%    12    50.0%       12      100.0%   100.0%
#     12   289  0.5009      26      60.6%    13    21.2%       12      100.0%   100.0%
#     14   231  0.4003      26      65.4%    12    27.1%       13      100.0%    75.0%
#     16    87  0.1508      28      46.4%    14     0.0%       13      100.0%     0.0%
#     18    70  0.1213      29      48.3%    14     0.0%       14      100.0%     0.0%
#     20    29  0.0503      30      46.7%    15     0.0%       14      100.0%     0.0%
#     22    29  0.0503      33      45.5%    17     0.0%       15      100.0%     0.0%
#     24    29  0.0503      35      47.1%    18     2.8%       16      100.0%     0.0%
#     26    29  0.0503      41      46.3%    21     0.0%       19      100.0%     0.0%
#     28    29  0.0503      48      45.8%    25     0.0%       22      100.0%     0.0%
#     30    29  0.0503      70      41.4%    39     0.0%       30       96.7%     0.0%
#
#   (1) U_(t-1) 覆盖率恒为 100% —— 不需要强制。这些 token 的 code 在上一步刚被
#       改写, 它们在 layer 3 的 V 因此变化最大, 打分自然把它们排在最前。LazyMAR
#       的 score[prev_mask_to_pred]=0 对这一半是纯冗余的。
#   (2) U_t 覆盖率从 step 16 起恒为 0% —— 真的被丢掉了。也就是说 step 16..30 的
#       每个 partial 步, 本步要 commit 的 token 用的都是上一步的陈旧 logit。
#       原因也清楚: U_t 的 code 此刻还是 mask, 打分时它的 V 与上一步一模一样,
#       永远排在最后。这是本次消融真正在测的东西 —— 而 FID 不但没崩, 还比每步都
#       把 U_t 算新鲜的 lazycache 更好。
#       解释: 到了这些 step, 一个仍被 mask 的 token 的 logit 在相邻两步之间几乎
#       不变 (每步只有 ~2% 的邻居被填上), 陈旧一步的代价远小于"中层多重算 25%
#       的 token"带来的收益 (31.4% vs 5.9%)。
#   (3) register 覆盖率从 step 16 起也是 0% —— attention sink 同样被冻住, 未见
#       可辨识的损失。
#
#   -> 对 Halton-MaskGIT 而言, LazyMAR 的强制集合不是这个方法起作用的原因;
#      起作用的是"用 V 的变化量把算力集中到真正在变的 token 上"+ 中层的总预算。
#
#   复现探针: 在 _forward_lazy 上挂 spy 记录 lazy_last_active_idx, 与
#   HaltonSampler.compute_schedule 给出的 l_U_t 求交 (batch 4, cfg=0.5, step=32,
#   REFRESH_N=2, L3-23)。
#
# 【下一步可试的杠杆】
#   - VSIM_SCHED 改成不含 1.0 的表 (如 "0.6,...,0.05"): step 6/8 那两个退化成
#     全量的 partial 步是纯浪费, 去掉后加速应能往 1.4x 走而 FID 变化不大。
#   - LAZY_START=1 (而非 3): 让 layer 1..23 都进 lazy 区间, 省掉 layer 1/2 的
#     每步全量; 打分材料仍然充足。
#   - 与 lazycache 的混合: 只把 U_t 加回强制集合 (U_(t-1) 已被打分自动覆盖),
#     成本仅 ~15/577 个名额, 可验证 (2) 的解释是否稳健。
